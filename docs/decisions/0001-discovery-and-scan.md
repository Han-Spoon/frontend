# ADR 0001: 식당 발견과 스캔 기록

날짜: 2026-09-10. 상태: 프론트 시연 구현; 실제 인증/서버 계약은 제안.

## 배경

사용자는 한국어 검색에 어려움이 있고, AI 팀은 스캔 전에 식당이 연결된 기록을 더 많이 원한다. 식당 연결을 강제하면 촬영하려는 순간 사용자가 이탈할 수 있다. 영수증 OCR과 외부 URL 복사 방식도 현재 범위와 맞지 않는다.

## 1. 홈에 검색바가 필요한가?

지역/지도/식단 탐색을 먼저 제공한다. 검색은 식당 선택 시트의 보조 기능으로 둔다. 검색 자체를 없애면 이미 이름을 아는 사용자에게 불편하다. 한글 원명+영문 표기+별칭을 하나의 식당 ID에 연결하고 점진적으로 alias를 추가한다. 모든 식당 설명을 7개 언어로 저장해야 검색이 가능한 것은 아니다.

## 2. 언제 식당을 지정하는가?

권장 시점은 스캔 직전. 홈의 식당 상세에서 스캔하면 이미 장소를 알고 있으므로 추가 입력이 없다. 직접 촬영에 들어온 경우 주변 후보를 1탭으로 고르거나 건너뛴다. 결과 저장 시 다시 제안하여 누락을 회수한다.

## 3. 기록과 피드백은 적합한가?

결과에서 “기록하기”는 “다시 스캔하기”와 동등한 크기로 유지한다. 메뉴 라이킷은 선호 저장, 기록하기는 스캔 보관으로 구별한다. 식당이 있으면 방문 연결 기록, 없으면 일반 기록이며 둘 다 스캔 기록에 모은다.

피드백은 일단 식당에서 식단 요청을 전달한 경험을 대상으로 한다. 등록 프로필 항목만 제시하고 yes/no/unknown으로 선택한다. 할랄/매운 음식 비선호라면 해당 두 항목만 표시한다. 식사 전 저장도 가능하므로 피드백은 필수가 아니다. 식단 대응 경험을 식재료 안전 확인으로 바꾸어 집계하지 않는다. 메뉴 자체의 맛/양 후기는 별도 후속 기능으로 둔다.

## 4. 식당 지정 없이는 스캔 불가로 해야 하는가?

강제하지 않는다. 식당 목록이 불완전하거나 위치 권한을 주지 않은 사람도 이용할 수 있어야 한다. 스캔 완료율을 유지하면서 연결률을 높이는 것이 목표다. 실제 데이터로 선지정률, 완료율, 저장 시 연결률을 비교한 뒤 재검토한다.

## 5. 실방문자는 어떻게 지정하고 검증하는가?

- 일반 식당: 동의한 위치 기반 근처 후보 → 사용자 1탭 선택 → 음식점 맥락이 채워진 촬영.
- 제휴 식당: 테이블/입구 QR → restaurantId 자동 연결 → 촬영. 앱 설치나 외부 URL 복사를 요구하지 않는다.
- 사용자가 찾지 못한 식당: 지역/영문 이름 검색, 후속으로 미등록 식당 추가 흐름.

사용자 선택이나 GPS 근처라는 이유만으로 방문 인증을 부여하지 않는다. 실제 인증이 필요하면 매장에 표시되는 짧은 유효기간의 서버 서명 QR 토큰, 스캔 세션 바인딩, 중복/재사용 방지를 구현한다. 정적 QR은 장소 자동 입력에는 유용하지만 현장 방문을 확실히 증명하지 못한다. 인증 수준을 self-reported / nearby / venue-verified 등으로 구분하고 노출 문구도 다르게 한다.

현 구현은 가상 지도와 사용자 선택만 제공한다. QR/위치 동의/서명 검증은 구현하지 않았다.

## 6. 스캔 전에 사용자 풀을 어떻게 늘리는가?

현재 홈은 지역 발견, 프로필 관련 경험, 식단별 랭킹, 식당 찜, 한식 콘텐츠를 제공한다. 촬영할 메뉴판이 없어도 여행 계획에 활용할 수 있다.

제휴가 생기면 지역 큐레이션·식단 요청 안내·예약 전 질문 카드·저장한 식당의 메뉴 변경 알림을 연결할 수 있다. QR 진입, 메뉴 정보 갱신, 식단 의사소통 피드백 대시보드를 식당에 제공하는 방향이 자연스럽다. 쿠폰은 후속 실험으로 두고 구매 여부와 후기/안전 랭킹을 섞지 않는다.

## 큐레이션 위치

메뉴마다 반복하면 광고처럼 보이고 판단 흐름을 끊는다. 결과 맨 아래 한 섹션만 두며 3개 이내로 추천한다. 제품의 핵심 행동 이후 자연스럽게 읽을 수 있도록 한다.

## 재검토할 지표

식당 선택 소요 시간, 선택 취소/건너뛰기율, 분석 시작/완료율, 저장률, 식당 연결률, 후기 참여율, QR 재사용 비율. 현재 수집 코드와 실제 지표는 없다.
